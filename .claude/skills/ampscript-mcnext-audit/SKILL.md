# AMPscript → Marketing Cloud Next Compatibility Audit

Produces two deliverables from a live MCE tenant:
1. A dark-themed, client-neutral PDF: one explainer page (stats, verdict bar, A–F legend,
   findings, recommended sequence) + appendix register of every email.
2. A CSV register: one row per email with verdict and functions to replace/redesign.

The framing goal of the report is **positive**: show the customer most of the estate is
buildable in Next, isolate the few genuine redesigns, and surface the one systemic fix.

## Prerequisites

- MCE MCP connector authenticated (tools named `sfmc_*`).
- Python with reportlab; `pdftoppm` for visual QA.
- Ask the user for the client/brand name to print on the report (header + footer).

## Workflow

### Step 1 — Establish the supported-function baseline

Read `references/mcnext-functions.md`. It contains the MC Next AMPscript function list
(Summer '26: 35 runtime-confirmed + 6 documented-but-untested), the native-replacement map,
and the redesign map. **The list changes with each release.** Offer to refresh it: web-search
"AMPscript functions Marketing Cloud Next" + the official Salesforce developer docs page, and
update the sets in `scripts/parse_ampscript.py` (SUPPORTED_CONFIRMED / SUPPORTED_UNTESTED)
if new functions have shipped. Note the release/date used in the report.

### Step 2 — Pull the email estate via the MCE MCP

Use `sfmc_get_content_assets` with `query_json`:

```json
{"$pagesize": 50, "$page": 1, "$fields": "id,name,assetType,views",
 "$filter": "assetType.name eq 'templatebasedemail'"}
```

Rules learned the hard way:
- Page through **three asset types**: `templatebasedemail`, `htmlemail`, `template`.
- `$pagesize` 25–50 only. Larger pages crash the connector with a Java heap error; if 50
  fails mid-run, drop to 25 and continue from the equivalent page.
- The first page returns `count` — use it to compute total pages per type.
- Large responses are stored as tool-result files rather than inline. Copy every stored file
  into a working directory (e.g. `out/content/assets/`) before parsing:
  Save each `sfmc_get_content_assets` result as a JSON file in `<workdir>/`.
- If a page comes back **inline** (small enough for context), do not lose it: immediately
  write the per-email function usage you can see into a supplementary JSON file in the
  workdir (`{"Email Name": ["Function1", "Function2"], ...}`) and pass it to the parser
  with `--extra`.
- Emails generated by Loyalty Management appear as many near-identical `htmlemail` copies
  per promotion code. If the tail pages are clearly repeats of patterns already captured,
  you may stop and note the coverage in the report (e.g. "41 of 61 read in full; remainder
  are Loyalty-generated copies").

### Step 3 — Parse and classify

Run `scripts/parse_ampscript.py --workdir <workdir> --out <outdir>`. It:
- Extracts every `%%[ ]%%` block and `%%= =%%` expression, collects function calls,
  ignores AMPscript keywords (SET/IF/FOR...).
- Filters false positives: any "function" matching a content-block name, timezone label,
  or other text artifact. Review its `--report-artifacts` output; add tenant-specific
  artifacts to the ARTIFACTS set if needed (dynamic-content block names ending in
  parentheses are the usual culprits).
- Scores each email A–F (see `references/mcnext-functions.md` for definitions) and writes
  `register.csv`, `verdicts.json`, and `census.json` (function → count).

Sanity-check the census before building the PDF: the top functions should be recognisable
AMPscript (Field, v, Empty, Concat, Lookup...). Anything odd = artifact to filter.

### Step 4 — Identify the story

Interrogate the results for the three headline elements (they generalise across tenants):
1. **The systemic unlock** — usually multi-row lookups (LookupRows family). Count how many
   E-verdict emails share it; the fix is pre-flattening data during the audience build.
2. **The validation gap** — heavy use of the documented-but-untested six (Lookup,
   ContentBlockById/Key/Name, RetrieveSalesforceObjects, RaiseError) → recommend a one-email
   runtime spike as the first build step.
3. **The genuine redesigns** — send-time writes/API calls (InsertDE, UpsertDE, HTTPPost*,
   HTTPGet, TreatAsContent in subject lines). Name each email and its fix individually.

### Step 5 — Build the PDF

Run `scripts/build_report.py --client "<Name>" --outdir <outdir> --register <register.csv>
--stats <stats.json>`. First write `stats.json` (see script header for schema) with the
headline numbers and the report copy for the two findings panels — tailor the copy to what
Step 4 found; never reuse another client's examples.

### Step 6 — Visual QA loop (mandatory)

Render and inspect before presenting; iterate until clean:
```bash
pdftoppm -png -r 60 report.pdf qa && <thumbnail + view page 1 and one appendix page>
```
Check: no text overflowing panel borders (panels are measured, but copy changes can still
push total height past the page), bar labels legible (narrow segments get leader lines), page-1
content ends above the footer. Zoom at 120–130 dpi on the bar and legend if in doubt.
Fix, rebuild, re-render. Two to three iterations is normal.

### Step 7 — Deliver

Copy the PDF and CSV to the outputs directory and present both. Summarise: total emails,
% with a clear path, the systemic fix, the named redesigns, and the recommended first step
(the validation spike).

## Failure modes

- **DE census / other objects denied**: only Content Builder access is needed; if other
  sfmc_* calls are denied, proceed — this audit needs assets only.
- **OutOfMemory on every page size**: fall back to per-asset fetch by ID, or reduce
  `$fields` to `id,name,assetType` and fetch `views` per asset.
- **No `pdftoppm`**: still QA by `pdftotext` + reportlab coordinate review, and say so.
